# QA spec → QA test case backlog

Requires the `qa-write-spec` skill in the same parent folder as this skill.

Human QA engineer scopes a site into test cases before anyone writes a test. Output is test cases — intent, priority, observable outcome — plus one Journeys note (step 2), plus one test cases index (step 10) in a backlog file todo.md. The qa-spec.md is a read-only input. Test cases hold no selectors and no test code; the config-gate templates and the Test file rules block's fixed lines are the only code this skill writes.

Files: read `qa-spec.md` from the test project root (ask the user if it isn't there). Write one file per test case, `<Test case ID>.md`, and `todo.md` into the **test cases folder**: `test-cases/` next to qa-spec.md, unless the user names another folder.

**Running scripts:** `<skill dir>` is this skill's base directory, the folder holding this SKILL.md (the path this file was opened from, without `SKILL.md`; when that path is unknown, the folder a file search for `qa-write-test-cases/SKILL.md` finds). Run every command from the test project root, so data paths like `qa-spec.md` resolve there.

## Backlog document

`todo.md` is the backlog document. It sits next to the test case `.md` files. Layout:

```
# QA test cases todo

<N> test cases from <test cases folder>/, grouped by feature. Each entry: (Priority, Tier[, Journey]).

> Generated by qa-write-test-cases on <today's date> — qa-write-test-cases keeps this file in sync: checkmarks and manual heading/ordering edits are preserved on its next run, but any other manual edit to a line's Title/Priority/Tier/Journey text is overwritten from the backlog.

## Journeys note

### Deferred journeys
- <Journey ID> — <name> (<roles>): <reason>

### Excluded
- <page, journey ID, or check name>: <reason>

### Spec gaps
- <one line per gap>

## <Feature>
- [ ] <Test case ID> — <Title> (<Priority>, <Tier>[, <Journey>])
```

- An empty subsection says `None`.
- A test case line's checkbox mark records implementation state. The agent implementing the test case sets it after ticking the test case's acceptance criteria:
  - `[ ]` — not implemented yet, or to be re-implemented: reset by "Re-run over an existing backlog", or it was documented from an existing test;
  - `[x]` — test file written and every acceptance criterion ticked;
  - `[?]` — partially implemented: some acceptance criteria not ticked (e.g. a missing credential); the test file may not exist yet. The unticked criteria in the test case show what is missing.

  This skill writes new lines as `[ ]` and never changes an existing mark (step 10), except resetting it to `[ ]` where "Re-run over an existing backlog" says so.
- `<journey ID>` comes from the spec.
- One `## <Feature>` heading per `Feature` value, one line per test case, both in spec order. A test case's spec position is the qa-spec.md entry it was derived from: its page's Site Map line, or, for a test case derived from a journey alone, its journey's heading, placed after every Site Map line in Journeys order. A Feature heading sits at the earliest spec position among its test cases. Within a Feature, test cases follow their spec positions; test cases at the same position follow by test case ID.
- `<Test case ID>` and `<Title>` are the two parts of the test case's heading (step 7). A `todo.md` line joins them with an em-dash (`<Test case ID> — <Title>`); the test case heading joins them with a hyphen (`<Test case ID> - <Title>`). `<Priority>`, `<Tier>` and `<Journey>` values are copied from the same-named attributes of the test case (step 7).

## Re-run over an existing backlog

If the test cases folder already holds test cases, treat them as the starting point:

- **Match before writing.** For each test case this run would write (step 7), look for an existing test case that tests the same thing: same Feature, lead role, angle (or OWASP category), entry point, and Journey. `python3 <skill dir>/scripts/qa_tickets.py index <test cases folder>` prints each existing test case's ID, Feature, Tier, Type, Journey, Projects and title on one line; open only the test cases whose Feature matches. A match keeps its ID and file.
- **Leave matched test cases unchanged** unless the spec change alters what they test. An unchanged test case keeps its text byte for byte, so its criteria hash and ticked criteria survive. The exception is a change to the hash recipe in `qa_tickets.py`: when step 10's `check` reports a stale hash on a test case this run left unchanged, run `python3 <skill dir>/scripts/qa_tickets.py rehash <test-case.md>` on it (or on the test cases folder when every stale test case is unchanged). It writes the current hash into the test case and into line 1 of its test file, keeping every mark, so the test case stays implemented. It resolves `**Test file:**` against the test cases folder's parent. It refuses a test case whose stored hash no earlier recipe reproduces from its current text, because its How to build or criteria were edited; a test case whose test file's line 1 doesn't carry the stored hash, because that test already lags the test case; and a test case marked `[x]` in `todo.md` whose test file is missing. Treat a refused test case as a changed test case. When a test case's How to build steps or acceptance criteria must change, edit them, recompute its criteria hash (step 7, Hash rule), untick all its criteria, and reset its `todo.md` mark to `[ ]`, so the implementer rebuilds the test case's test.
- **Refresh the automation fields of every matched test case** from the current Playwright config gate, even when nothing else changes: `**Projects:**`, `**Test file:**`, and the Test file rules block (step 7). `**Projects:**` and `**Test file:**` are outside the hashed text (step 7, Hash rule). The Test file rules block is part of How to build, so a change to it — a new Test file path, session, or self-skip line — follows the rule above, and the implementer moves or updates the test file.
- **Number new test cases after the highest existing number** in their CATEGORY. Never reuse a number, even one left free by a deleted test case.
- **Obsolete test cases** — a test case whose source item is gone from the spec or is now marked `Excluded:` — are listed to the user, who decides whether to delete them. A test case whose behavior is listed under `todo.md`'s Spec gaps is not obsolete: it documents a tested behavior that the spec has no entry for. Delete only the ones the user confirms. Name each one's test file (its `**Test file:**`) in the list, since deleting the test case leaves that file without a test case.
- **Update `todo.md`** per step 10.

## Playwright config gate

Run this gate before step 0. Test files written from these test cases must land in configured Playwright projects, so the backlog is only written against a config that guarantees it.

1. Read the header of qa-spec.md: its `Roles crawled:` and `Environments:` lines. `no-login` is an exception: it never appears in `Roles crawled:`, and this gate adds it for every spec. If there is no `Environments:` line, stop and ask the user to re-run `qa-write-spec` to record the supported environments.
2. Slug the names: a role or an environment's Playwright profile name is lowercased with spaces turned into hyphens (`standard user` → `standard-user`, `Desktop Chrome` → `desktop-chrome`, `iPhone 13` → `iphone-13`). `<role>` in folder paths and project names is always the slug, and `<tests root>` is the config's top-level `testDir`.

3. Find the Playwright config at the test project root (`playwright.config.ts`, `.js`, `.mts`, `.mjs`, `.cts`, or `.cjs`). Run `python3 <skill dir>/scripts/qa_projects.py check-config --spec qa-spec.md --project-dir .`: it checks the project names and each project's role folder, and prints `<tests root>`. Check the rest by reading the config. It passes when:
   - its `reporter` includes `['json', { outputFile: '<path>' }]` on every branch it can take (e.g. both sides of `process.env.CI ? … : …`);
   - it loads `.env` (e.g. `import 'dotenv/config'`) and sets `use.baseURL` and `use.screenshot: 'only-on-failure'`;
   - it has one project named `<role>-<environment>` for every crawled role, plus the artificial role `no-login`, and every environment;
   - each such project sets `testDir` to that role's folder (`<tests root>/<role>`), `use` to the environment's Playwright profile with `defaultBrowserType: 'chromium'` (every environment runs in Chromium) and the role's `storageState`, and depends on the setup project; `no-login` projects set no `storageState`, so their tests start logged out.
4. Find the setup file that the role projects depend on (the `testMatch` of their setup project, under the config's `testDir`, e.g. `tests/auth.setup.ts`). It passes when it exists, logs in every crawled role, and writes each role's session to the `storageState` path its projects use — the template imports the role list from the config, so the two stay in step. The project's `.gitignore` lists `.auth/`, since the session files hold live cookies.
5. If the config or the setup file is missing or fails any check, stop and write no test cases. List every failed check. For a config that follows the template but names other roles or environments, show the diff from `python3 <skill dir>/scripts/qa_projects.py fix-config --spec qa-spec.md --project-dir .`; if the user agrees, run it again with `--apply`, which writes the config and re-runs `check-config`. Otherwise show [`templates/playwright.config.ts`](templates/playwright.config.ts) and [`templates/auth.setup.ts`](templates/auth.setup.ts) filled in with this spec's roles and environments — for an existing file, as a diff against it. Edit either file only after the user agrees, then commit the edited files at once (`git add -- <files>`, `git commit -m "qa-write-test-cases: fix Playwright config"`).

## Steps

0. **Check the exclusions.** Before any other work, check the Journeys section exists: if qa-spec.md has none, stop and ask for the spec to be completed (re-run `qa-write-spec`) before writing test cases. Then run `python3 <skill dir>/../qa-write-spec/scripts/qa_spec.py qa-spec.md`. Exit 1 or 3: stop, show the lines it printed, and ask the user to fix qa-spec.md — a hand edit since the crawl may have broken it. Exit 2: show its warnings to the user and continue, reading the lines they name by hand in the steps below. The script checks `Excluded:` on Site Map route lines against the journey chains. Then read every other `Excluded: <reason>` line the user added to qa-spec.md, on a page's Per-page test guidance heading, a journey, or a cross-cutting check (`qa-write-spec` Exclusion grammar), and check each page excluded under its guidance heading against the journey chains. If it is a step in the chain of a named journey (step 2), stop with an error and write no test cases. The error names the page, the journey and the reason, and asks the user to fix qa-spec.md: remove the page's `Excluded:` line, change the journey's chain, or mark the journey `Excluded:` or `Deferred:`. Done when no such page remains.

1. **Inventory the surface.** From the map, list every page, every user role, and every state-changing action (form submit, payment, auth, upload, delete, permission change). Everything marked `Excluded:` (step 0) is left out: no inventory entry, no test case, and it is listed in the Journeys note (step 2). Done when every node in the map without an `Excluded:` line has an inventory entry — nothing skipped, including admin/internal pages.

2. **Reconcile the critical journeys.** A journey is a chain across the inventory that delivers a business goal end-to-end (signup → first action, browse → checkout, login → dashboard → edit → save). The spec's Journeys section (from `qa-write-spec`) is the source of truth for which journeys exist: take each journey's ID, name, roles and chain as written. Reconcile it against the inventory from step 1:
   - **Journey in the spec, marked neither `Deferred:` nor `Excluded:`** — becomes a **named journey** for the rest of these steps, unchanged.
   - **Journey marked `Deferred:`** — not a named journey: no Journey-level test case and no journey OWASP pass (step 4). List it in the Journeys note with its reason.
   - **Journey marked `Excluded:`** — treated like a `Deferred:` journey (no Journey-level test case, no journey OWASP pass), listed in the Journeys note as excluded with its reason instead of waiting on a role.
   - **Chain step not in the inventory** — only on a `Deferred:` or `Excluded:` journey, since step 0's lint rejects it elsewhere: keep the journey, and list the step as a spec gap in the Journeys note.
   - **Business goal visible in the map with no journey in the spec** — list it as a spec gap in the Journeys note; its pages still get Interaction-level test cases.

   The **Journeys note** is written into `todo.md` (layout in "Backlog document") and collects deferred journeys (ID, name, reason), excluded items (pages, journeys, checks) and spec gaps. Done when every spec journey is either named, listed as deferred, or listed as excluded, and every mismatch is listed as a spec gap.

3. **Pick test angles per inventory item.** For each item, decide which of these apply — most items need several. **Security and Performance always get their own separate test case(s), never grouped with anything else or with each other.** Security specifically can produce several separate test cases per item — one per applicable OWASP category (step 4) — never merged into a single Security test case. Functional/Boundary/Negative/Cross-cutting angles on the same item may share one test case — but test isolation (step 6) is the hard rule: the moment two angles need different Arrange (different role, different starting data, different prior state), split them into separate test cases. Same setup groups; different setup always splits.
   - **Functional** — does it do what it claims, on the happy path.
   - **Boundary** — behavior at the edges: empty, minimum, maximum, one-past-maximum, wrong type.
   - **Negative** — behavior under misuse: wrong order of steps, double-submit, back-button, expired session.
   - **Cross-cutting** — accessibility (keyboard/screen-reader reachable). A layout check across environments needs no test case of its own: every test case runs in every environment its `**Projects:**` lists — all of them unless an Environment differences entry narrows it (step 6).
   - **Security** — any item that takes input, holds auth, or moves data. Scope is fixed, not open-ended: OWASP Top 10:2025 coverage, input validation, authentication/authorization checks, data protection — run it through the OWASP checklist below.
   - **Performance** — only for items the map flags as high-traffic or data-heavy; don't apply everywhere.

4. **OWASP checklist — run it on every input/auth/data surface, inventory items AND named journeys.** Some categories (Broken Access Control, Authentication Failures) only surface across a multi-step journey, not at single-item granularity — run the checklist against each named journey from step 2 as well as each inventory item from step 1. For each surface where a category applies, write one test case per category. A protection enabled once in config needs one test case proving it on a representative surface, not one per surface. The categories are [OWASP Top 10:2025](https://top10.owasp.org/2025/) — use this edition's IDs and names, and its category pages for what each covers; each row's "applies when" decides whether it applies to this project:

   1. **A01: Broken Access Control** — applies when roles or data ownership differ, or the app fetches a user-supplied URL: privilege escalation, another user's record by ID (IDOR), forced browsing to admin routes, CSRF, SSRF
   2. **A02: Security Misconfiguration** — applies to every deployed app: default credentials, missing security headers, permissive CORS, directory listing
   3. **A03: Software Supply Chain Failures** — applies when the UI or response headers disclose component names or versions (about page, `X-Powered-By`); dependency scanning itself is outside this backlog
   4. **A04: Cryptographic Failures** — applies when the app handles credentials or sensitive data: HTTPS and HSTS, secure cookie flags, password hashing, no secrets in URLs
   5. **A05: Injection** — applies when input reaches a query, template, or command: SQL injection, XSS, command injection
   6. **A06: Insecure Design** — applies when a flow can be abused as designed: rate limiting, anomaly detection, business-rule bypass
   7. **A07: Authentication Failures** — applies when users log in: session hijacking, session fixation, weak password or reset flow
   8. **A08: Software or Data Integrity Failures** — not in this checklist. Business data integrity (cascades, double billing, inconsistent related state) is a product flaw, not security: cover it with Functional or Negative test cases, not `SEC` test cases
   9. **A09: Security Logging and Alerting Failures** — applies when the app keeps an audit or security log a tester can inspect
   10. **A10: Mishandling of Exceptional Conditions** — applies when an error path is reachable from the UI: stack traces or system errors shown to the user, failing open when a check errors

   **OWASP target:** at least 90% of the applicable categories tested. Decide applicability per project from each row's "applies when"; A08 is never applicable. A category is tested when at least one test case covers it. `qa-review-test-cases` checks this target.

5. **Tier ratio — weight the backlog across two tiers, roughly 20% Journey-level / 80% Interaction-level**. Security and Performance test cases (step 3) sit outside this ratio entirely — excluded from the count on both sides. Still tag them Journey-level or Interaction-level per where they were derived from, for `Feature` grouping — just don't count them toward the 20/80 split:
   - **Journey-level** (~20%) — walks a full named journey end to end. Catches what only shows up across steps: state carried forward, session/timing issues, whether the end goal is reachable at all.
   - **Interaction-level** (~80%) — exercises one shared component from a single entry point, or two components on the same page, without walking a full journey. A component reached from multiple entry points (e.g. "add to cart" from the product page vs. from search results) is one test case per entry point, per test isolation — each entry point is different Arrange, so it's a separate test case, not one test case doing two Acts. Tag each with the same `**Feature:**` value (step 7) so they're findable together despite being separate test cases. Don't drop this tier despite the smaller per-test-case scope — journey test cases only visit each component once, from one direction, and will walk right past a bug that only shows up on another entry point.

6. **Hold every test case to this baseline discipline**, regardless of tier or type:
   - **Isolation** — Arrange establishes self-contained state; never assume another test case's leftover data or an active session left behind by a prior test. State the cleanup this test case requires as a `**Cleanup:**` line in How to build (step 7), which the criteria hash covers; if none is needed, say so there.
   - **Fail fast on error paths** — for any test case testing a failure, Assert and UX behavior must check the failure is immediate and visible (an error message, a rejected request), never that the system silently falls back to cached, mock, or default data.
   - **No production data** — Arrange specifies synthetic or environment-scoped test data, never a real customer/user record.
   - **No fragile hard-coded data** — Arrange describes the shape of data needed (a card the sandbox declines, a project name that won't collide with fixtures), not one brittle specific value the environment might not have.
   - **Document the environment** — the environments a test case runs in are its `**Projects:**` (step 7); Arrange names locale or other conditions whenever the outcome could vary by them. Never hand-write browser or viewport sizes: screen sizes come from the Playwright device profiles in the spec's `Environments:` line. **Environment split:** any test case whose Arrange, Act, or asserts depend on a fact in one of qa-spec.md's Environment differences entries is split per combination of those entries' breakpoints, each standing for the environments its entry lists: each test case's `**Projects:**` lists exactly the environments its combination shares, and a combination that shares none gets no test case.
   - **Don't silently skip a test case** — every item from steps 1-2 gets one (a `Deferred:` journey is listed as deferred, an `Excluded:` item as excluded, instead); an "obvious" case left unwritten is invisible to everyone but you.

7. **Write each test case self-contained** — no separate test-case document to reference; the test case is the spec. If you have a backlog test case template (the user's or the project's), read it first and keep its mandatory sections and its own rules (checkbox format, empty markers) — re-check the mapping below against whatever it currently requires. Without one, the sections below, in this order, are the whole format. Either way, this skill fixes where QA-test-case content goes:

   - **Test case ID format** — `TC-[CATEGORY]-[NUMBER]`, where CATEGORY is uppercase letters and digits and NUMBER is 3 digits, zero-padded, counted per CATEGORY from `001`:

     ```
     Examples:
     - TC-CLI-001 (CLI tests)
     - TC-WEB-042 (Web tests)
     - TC-API-103 (API tests)
     - TC-SEC-007 (Security tests)
     ```

     CATEGORY isn't limited to these four — use whichever fits the inventory item (pick a closer one when it fits) — but always use `SEC` for any test case produced by step 4's OWASP checklist regardless of surface.
   - **Heading** — `## <Test case ID> - <Title>`, where `<Title>` is an outcome-readable title. Each section from Parent to Potential Bugs is a `### <section name>` heading (e.g. `### How to build`), with no other `##` or `###` heading inside a section.
   - **Directly under the heading, before Parent** — add `**Priority:** <P0-P3>` (step 8), `**Tier:** <Journey-level/Interaction-level>` (step 5), `**Type:** <one or more of Functional/Boundary/Negative/Cross-cutting/Security/Performance>` (step 3), `**Estimated Time:** <rough manual-execution minutes>` (a backlog-sequencing aid, not a gate), and `**Feature:** <shared component or feature name>` — mandatory on every test case, not only ones isolation forced apart; lets test cases sharing a component (same entry point or split across several) be found together. A Journey-level test case that walks a named journey also carries `**Journey:** <journey ID from the spec>`. **Projects rule:** every test case also carries `**Projects:** <project>, …` — the lead role's project for every environment — or, for a test case that depends on Environment differences entries, exactly the environments the Environment split (step 6) gives it — named as in the Playwright config gate (e.g. `admin-desktop-chrome, admin-iphone-13`); the lead role is `no-login` when the test starts logged out (login page, password reset, a logged-out user's redirects). **Test file rule:** every test case also carries `**Test file:** <tests root>/<role>/<Test case ID>.spec.ts` — the exact path, directly in the role folder; the role folder makes the file run in every project of that role. When Projects lists some but not all of the role's environments, the test skips itself in every other project (Test file rules block).

     None of these fields are part of the generic template; they're specific to this skill's test cases.
   - **Write order and back-references** — write Journey-level test cases first, then Interaction-level ones, each in spec order (Backlog document). Parent, Relates to and Blocked by cite only a test case that already exists: one kept from an earlier run, or one written earlier in this run. Test case numbers can't show this order, because each CATEGORY counts separately, so this rule replaces a template's lower-number rule.
   - **Parent** — the Journey-level test case this one descends from, if this is an Interaction-level test case scoped under a named journey. Omit it when there is none (the template's omission rule, else leave the section out).
   - **What to build** — the user story: role, action, and the "so that" clause drawn from the journey or business goal (step 2) this test case serves.
   - **How to build** — Arrange-Act read as test case fields: **Arrange** (the state the world must be in before the test starts: role, data, prior step) and **Act** (what the user/tester does, as a sequence, in plain terms) and **Cleanup** (step 6), plus any constraint on how the test must be run that would otherwise let a false pass through (e.g. "use the real sandbox response, not a mock"). Arrange never lists a UI login for the lead role: the session comes from the project. Then a **Test file** block, filled in for this test case and repeated in every test case, so the implementer needs nothing beyond the test case:

     ```markdown
     **Test file rules:**
     - Write exactly one file at `<Test file>`. Every test in it belongs to this test case, and every test title starts with `<Test case ID>: `.
     - Line 1 of the file is the comment named in the acceptance criteria's `Output test file contains comment` item.
     - The Playwright project supplies the browser or device: never set a viewport, user agent, or device in the test.
     - Session: <exactly one of>
       - Starts logged in as <role>: the project injects the session. Do not log in through the UI.
       - Starts logged out (`no-login`): there is no session. Log in through the UI only where an Act step says so, with credentials from `process.env.<ROLE>_USERNAME` and `process.env.<ROLE>_PASSWORD` (`.env`, loaded by the Playwright config; `<ROLE>` is the role name uppercased, with every character other than a letter or digit turned into `_`, e.g. `ADMIN`, `CUSTOMER_RESTRICTED`), never literal values.
     - <only with a helper role: a crawled role other than the lead role> The <helper role> steps run in a second browser context: `const helper = await browser.newContext({ storageState: '<helper role's storageState path from the Playwright config>' })`, closed at the end of the test.
     - <only with logged-out steps besides the lead role's> The logged-out steps run in a second browser context with no session: `const guest = await browser.newContext({ storageState: { cookies: [], origins: [] } })`, closed at the end of the test. A plain `browser.newContext()` inherits the project's session. A UI login in it takes credentials from `process.env.<ROLE>_USERNAME` and `process.env.<ROLE>_PASSWORD`, as on the logged-out Session line.
     - <only when Projects lists some but not all of the role's environments> The first line of every test is `test.skip(!['<project>', …].includes(test.info().project.name), '<reason>')`.
     - Do not edit the Playwright config or other test cases' test files.
     ```

     Drop the lines marked "only …" when they don't apply, and replace every `<…>` with this test case's values.
   - **Acceptance criteria** — lead with **Assert:**, then one checkbox list, each item binary pass/fail, observable, no prose intent. For everything step 3's Negative/Security angles say must NOT happen or must stay unchanged, add an item to this same list prefixed `Absence check:` — a separate section is not the template's shape; a positive item announces itself when missing, an absence item doesn't unless it's written down. No overall pass/fail summary line ("PASS if all items above pass, FAIL otherwise"): the checkbox list already implies it. Name every spec-stated value the test checks (a length limit, a boundary value) in the criterion or How to build step that uses it: the other sections, UX behavior included, are outside the hash.
   - **UX behavior** — the observable states/surfaces/error paths a user would see, distinct from the pass/fail checklist. If the test case is backend/security-only with nothing a user sees, use the template's "no visible surface" marker, else `No user-facing surface` plus what the test checks instead.
   - **Relates to** — other TC test cases worth reading alongside this one for context, even outside this test case's own Feature (e.g. a Journey-level test case relating to an Interaction-level test case for a component that journey passes through), one per line, else `None`. Back-references only (write order above).
   - **Blocked by** — any already-written test case that must land first (e.g. a permission-model test case this one assumes exists), one per line, else `None — can start immediately`.
   - **Potential Bugs** (last, after Blocked by) — edge cases or security concerns adjacent to this test case that aren't already an Acceptance criteria item. Flags risk for whoever executes or automates the test case without forcing every guess into a formal checklist item.

   Example (Acceptance criteria only):
   - [ ] Payment decline shows an on-page message naming the reason, cart and shipping details intact
   - [ ] Absence check: retrying with a different card does not require re-entering shipping info
   - [ ] Absence check: no stack trace or raw processor error reaches the page
   - [ ] Output test file contains comment: `// TC-WEB-042 criteria-hash: <hash>` as its first line

   Together, this list is the whole mechanism for redoing the test later — describe outcomes, never the mechanism that produces them. The last item is the drift guard: once a test case is automated, editing this list or the How to build steps changes the hash, so the test file's first line goes stale and shows the test needs rebuilding.

   **Hash rule.** `<hash>` fingerprints what the test does and asserts: every How to build line, Test file rules block included, and every Acceptance criteria line except `>` notes; blank lines and trailing spaces don't count, and each section ends at the next `##` or `###` heading. The hashed text excludes the `Output test file contains comment` criterion itself, which breaks the circle of a hash covering its own line, and excludes checkbox marks, so ticking a criterion off leaves the hash unchanged. `<skill dir>/scripts/qa_tickets.py` owns the recipe: `python3 <skill dir>/scripts/qa_tickets.py write <test-case.md>` writes the computed value into that criterion and prints the test file's first line, `hash` prints that line, `check <test cases folder>` lists test cases whose stored hash is missing or stale, and `rehash` moves an unchanged test case and its test file onto a changed recipe (Re-run over an existing backlog). The test file carries the same value as its first line. Whenever this skill adds or changes a test case's How to build steps or acceptance criteria — in this step, in step 9's closing pass, or on a re-run — recompute the hash and rewrite it as the last edit to that test case.

8. **Assign priority — Priority scale:** the severity of the defect the test would catch.

   - **P0** — the test guards a permission decision, a destructive action, data loss, or an OWASP category.
   - **P1** — a core journey step.
   - **P2** — a secondary feature or an edge case.
   - **P3** — cosmetic.

   Tie-breaks: a `SEC` test case is P0; a named journey's Journey-level test case is at least P1.

9. **Close the backlog against this bar** before calling it done:
    - Every named journey has at least one Journey-level test case carrying its Journey ID (compared numerically: `J01` and `J1` are the same ID), and every named journey has also been run through the OWASP checklist (step 4), not just its inventory items.
    - Every input/auth/data surface (items AND journeys) has been checked row-by-row against the OWASP checklist (step 4). A protection enabled once in config needs one test case proving it on a representative surface, not one per surface.
    - No test case groups Security or Performance with another angle; no test case groups two angles that needed different Arrange (step 3).
    - Every Interaction-level test case on a component reached from multiple entry points is split one-test-case-per-entry-point, each carrying a matching `Feature` value (step 5).
    - Every test case carries Priority, Tier, Type, Estimated Time, Feature, Projects, and Test file, plus a filled-in Test file rules block with no `<…>` left (and Journey on each Journey-level test case that walks a named journey), and an outcome a non-technical reader would recognize as pass/fail.
    - Every test case follows step 6's baseline discipline — cleanup stated (or stated as none needed), no production data, no fragile hard-coded data, environment documented where it matters, no silently-skipped item.

10. **Complete `todo.md`** after the test cases are final. Every test case appears exactly once in `todo.md`.
    If `todo.md` already exists, update it in place instead of rewriting it:
    - Keep each test case line's checkbox mark as it is, except where "Re-run over an existing backlog" resets it to `[ ]`.
    - Keep manual heading and ordering edits under the `## <Feature>` headings.
    - Rewrite each kept line's Title, Priority, Tier and Journey from its test case.
    - Add a line for each test case new since the last run under its Feature heading, at its spec position among the lines there (Backlog document); a new Feature heading goes at its spec position among the headings.
    - Drop the line of each test case no longer in the backlog.
    - In the Journeys note, drop each deferred or excluded entry whose journey, page, or check qa-spec.md no longer marks `Deferred:` or `Excluded:`, drop each spec-gap line qa-spec.md now resolves (the item is now excluded, deferred, on a journey, or stated in the spec, e.g. as a Site Map page or an Environment differences entry), and add the entries from step 2 not already listed.
    - Refresh the test case count in the header line and the date in the generated note.

    If no `todo.md` exists yet, create one according to the layout of "Backlog document": add the title, header line and generated note above the Journeys note from step 2, then one line per test case under its Feature heading.

    Last gate, once `todo.md` is final: `python3 <skill dir>/scripts/qa_tickets.py check <test cases folder>` and `python3 <skill dir>/scripts/qa_projects.py check-test-cases --spec qa-spec.md --tests-root <tests root> <test cases folder>` both exit 0: every stored criteria hash is current; no How to build keeps a Test file rules block `<…>` placeholder; every test case carries Priority (P0–P3, step 8), Tier (Journey-level or Interaction-level, step 5), Type, and Feature, none left as its `<…>` placeholder; `todo.md` exists and lists every test case exactly once; and every test case's Projects, Test file, and self-skip line follow step 7.

    **Commit** once the last gate passes: `git add -- <test cases folder>` (the new, changed and rehashed test cases, deletions the user confirmed, and `todo.md`), then `git commit -m "qa-write-test-cases: write test cases"` (`qa-write-test-cases: update test cases` over an existing backlog). Add only that folder; changes the user made elsewhere stay uncommitted.

## Parallel authoring

Optional, and only when the agent can run subagents and the backlog is too large for one agent to write comfortably. Otherwise one agent runs every step in order. **Main** is the agent running this skill; a **subagent** is a fresh agent that gets a self-contained prompt.

The steps that need the whole backlog stay with Main alone: the exclusions check and inventory (steps 0–1), the journeys (2), the angles (3), the OWASP checklist (4), the tier ratio (5), the baseline discipline (6), the priorities (8), closing the backlog (9), and `todo.md` with the last gate (10). Only step 7, writing each test case, runs in parallel.

1. **Main builds a work list** after step 6 and 8: one line per test case to write, with its **ID already assigned** (Main numbers per CATEGORY after the highest existing number, and never reuses one), title, Feature, lead role, angle or OWASP category, Journey, Tier, Priority, and the `qa-spec.md` entries it derives from. Main cuts the list into slices, one per Feature or group of Features.
2. **Each subagent writes its slice.** Its prompt holds the slice, this skill's step 7 rules, the Playwright config gate's results (Projects, Test file, self-skip line), and the test cases folder. It writes only the `<ID>.md` files its slice names, runs `qa_tickets.py write <test-case.md>` on each, and returns the list of files written and any behavior the spec lacks, as text.
3. **A subagent never** edits `qa-spec.md`, the Playwright config or setup file, `todo.md`, or a test case outside its slice; assigns or changes an ID; or changes a Tier or Priority from the list.
4. **Main closes.** After every subagent returns, Main reads the new files, checks step 9 across all slices (journey coverage, OWASP target, tier ratio, no duplicates between slices), fixes what fails by writing or merging itself or by sending one slice back, records the returned spec gaps in `todo.md`'s Journeys note, then does step 10 and the last gate.

Every file has one writer at a time: each test case file belongs to one subagent; `qa-spec.md`, the config, the setup file and `todo.md` belong to Main.
