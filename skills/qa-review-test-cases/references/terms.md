# Terms

Used throughout SKILL.md and every subagent prompt.

- **Page** — a screen with its own URL that the user navigates to.
- **Action** — any request a page fires without opening its own screen (form post, modal, background/API call). An action belongs to the seam of the page that triggers it, whatever its path or mode.
- **Seam** — a Site Map entry, resolved to its code entry points in Step 1.3. A seam made of independent forms or tabs is split into sub-seams.
- **Behavior** — one user-observable outcome (a validation rule, a permission decision, a state change, an error path). Branches producing the same outcome are one behavior. Validation is grouped per form per constraint family.
- **Covered** — a behavior is covered only by a test case with an Act step that exercises it plus an assert that pins its observable outcome. Mentions in Potential Bugs, Arrange, Cleanup, or constraints don't count; neither does a hedged "either X or Y" assert (reported as HEDGED ASSERT); neither does a test case reported as CONTRADICTED (the whole test case) or an assert reported as EXPECTATION WRONG (that assert only — the test case's other asserts still count). A security test case the app fails still counts as coverage — it will catch the defect. An Environment-differences fact is covered only by test cases whose `**Projects:**` lie within that entry's environments, together span them, and whose asserts pin the fact. A behavior pinned only by a HEDGED ASSERT or EXPECTATION WRONG finding is reported only as that finding, never also as a missing test case. Main recomputes the COVERAGE counts after applying D's verdicts, counting a HEDGED ASSERT or EXPECTATION WRONG that D downgrades or refutes as covered.
- **Permission decision** — an authorization check whose outcome depends on the role or on who owns the data.
- **Destructive action** — deletes records, or irreversibly discards data the user did not explicitly choose to replace.
- **Security test case / security behavior** — decided by substance, using the [OWASP Top 10:2025](https://top10.owasp.org/2025/) category definitions: a test case (or code behavior) is security when its asserted outcome falls under an OWASP category of the `qa-write-test-cases` OWASP checklist — whatever its ID prefix or Type label. Data integrity is not security (`qa-write-test-cases` OWASP checklist): it follows code-as-truth, and surprising integrity behavior is a Product smell. A test case asserting, e.g., that invoiced entries are not billed twice is therefore non-normative unless it also asserts an OWASP-category outcome.
- **Expected-outcome authority** — the goal is test cases that catch regressions, so for non-security test cases (Functional, Boundary, Negative, Performance, whatever their label) the app's current code behavior is the truth: a test case expecting a different outcome is wrong. **Security test cases are the exception:** they are normative, and their expected outcome overrides the code; when the code doesn't meet it, the app is at fault (Step 1.9), not the test case.
- **Product smell** — current behavior that a test case must pin (because code is the truth) but that a user would not expect: the UI reports success while less happened; a destructive effect without confirmation; a cascade beyond what the user chose; a misleading message; input silently changed; a silent, permanent degradation; related state left inconsistent; code that contradicts a spec clause; code paths that conflict on the same input. Security behavior is never a smell — it is a Blocker or Error through APP FAILS SECURITY TEST CASE or INSECURE BEHAVIOR, no test case (Step 1.9).
- **Named journey** — a journey in qa-spec.md's Journeys section marked neither `Deferred:` nor `Excluded:` (`qa-write-test-cases` "Reconcile the critical journeys"). Any other journey, or one not in the Journeys section, is an **out-of-scope journey**.
- **Security findings** — every Blocker or Error that is APP FAILS SECURITY TEST CASE, INSECURE BEHAVIOR, no test case, a missing OWASP test case, OWASP TARGET MISSED, or a HEDGED ASSERT on a security test case. The report copies them into Security Blockers and Security Errors.
- **In-scope role** — a role listed under "Roles crawled" in qa-spec.md's header; these roles lead. The artificial role `no-login` (the logged-out state, from `qa-write-test-cases`' Playwright config gate) is always in scope; it maps to anonymous access, not to a code role. A role listed under "Roles not crawled" is a **deferred role**: one Warning, never lead scope. A test case may use any other app role as a **helper** when it needs one to validate an in-scope behavior (e.g. a lower role proving an access boundary); such test cases count as coverage.
